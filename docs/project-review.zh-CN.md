# Code Link 与高星项目的实际差距

2026-11-14 核对了本地源码、真实界面截图、构建脚本，以及同类项目的 README 和 GitHub API。查询时，目标仓库创建约一天、尚无首次提交、0 Star。这个状态首先说明项目尚未公开交付，无法据此判断用户试用后的满意度。星数快照保存在 [github-benchmarks.json](github-benchmarks.json)。

## 对比对象怎么选

| 项目 | 查询时 Star | 对比的理由 | 可以借鉴的做法 |
| --- | --- | --- | --- |
| [Happy](https://github.com/slopus/happy) | 24,634 | 同样让用户从移动端继续处理电脑上的代理任务，属于更直接的竞争对象 | 首页视频、移动端延续同一会话、多平台与多种代理、明确的安装入口 |
| [LocalSend](https://github.com/localsend/localsend) | 98,886 | 同样强调设备间本地连接，适合比较安装与产品说明 | 一句话表达用途，多语言与各平台下载矩阵，签名和包管理器分发 |
| [scrcpy](https://github.com/Genymobile/scrcpy) | 154,766 | 同样涉及 Android、USB、桌面工具与设备控制 | 直接展示真实画面，列出可验证的性能和兼容条件，按平台组织安装与排障 |
| [Vibe Kanban](https://github.com/BloopAI/vibe-kanban) | 28,678 | 适合比较多任务管理、结果审查和初次启动 | 一条命令启动，将工作规划、代理执行和 diff 审查组织成连续流程 |

这些项目的用途、上线时间和传播基础不同，星数只作背景。查询时 Vibe Kanban 首页已经标明停止运营计划，仍可参考其交互组织，选型应另行判断维护状态。这里对竞争产品的功能描述来自其维护者文档，并未完成全部产品的上手测评。

## 为什么现在没有高星

最直接的障碍是公开入口尚未建立。此次工作前，GitHub 上没有代码、README、Release、About 或 Topics。本地已有详细文档与多轮真机验收，访客无法看到这些材料，也无法从仓库下载试用。

公开之后，仍有几个会影响尝试和持续使用的条件。Windows 电脑、Android 设备、本地连接、安装两个客户端，再加上 USB 调试和 .NET Runtime，适用人群经过了多次筛选。产品还只提供中文界面，英文 README 能帮助理解，却不能解决操作障碍。与覆盖更多设备和代理的 Happy 比，Code Link 需要把本地直连、接入已有窗口与分组提醒的价值展示得更具体。

目前缺少仓库访问、下载、首次连接成功和再次使用的数据，不能把某项功能或配色认定为低星的原因。可以先检验访客是否看懂、下载后能否连接，以及连接后是否愿意继续用。

## 已有的基础

Code Link 已有可工作的 Windows WPF 托盘工具与 Android 原生客户端。USB、蓝牙、输入回传和结构化 Codex 授权都有实现；提醒状态区分成功、失败、中断、未知和断线，避免把安静的终端误报为完成。A 组逐个提醒、B 组整轮成功后提醒，是值得继续打磨的实际使用差异。

仓库也已有中文和英文说明、真实截图、许可证、贡献和安全文档、可固定哈希的依赖下载，以及后台接收的验收记录。这些比单纯的界面原型更有基础。当前记录主要来自一台 Android 14 / ZUI 16 平板，USB 连续连接有一轮 89 分钟证据；还需要更多设备和更长连接时间来支持广泛兼容的说法。

## 功能设计缺在哪

| 观察 | 对用户的影响 | 优先处理 |
| --- | --- | --- |
| 安装两个客户端、额外安装 Runtime、USB 调试授权 | 第一次看到价值前已经要完成多项准备 | 包含运行时的桌面包、连接向导、每一步显示成功状态 |
| 任意终端没有统一的任务结束协议 | 用户期待每条命令都能提醒，实际可能保持未知 | 在选择终端时解释当前检测方式，提供明确的托管命令入口 |
| 外部 Windows Terminal 跟随活动标签页 | 切换标签会改变观察对象，多个任务容易混淆 | 标明当前观察窗口与限制，优先引导独立窗口或托管会话 |
| 通用终端、结构化授权与 A/B 规则同时出现 | 新用户需要先理解多套概念 | 默认跑通一个任务，再引导完成提醒与分组 |
| 查看输出后主要依靠文本继续工作 | 代理用户还需要了解改了哪些文件和测试结果 | 根据用户需求试做文件变更摘要与 diff 查看，不急于重造完整 IDE |
| LAN、蓝牙锁屏、多厂商后台缺少完整验收 | 离开当前真机组合后体验不确定 | 公布设备测试矩阵和失败记录，验证长连接、重连和耗电 |

## 界面具体缺在哪

根据真实截图与布局源码，两端使用同一套米白、深绿和黄色，已经具有一致性。桌面端把终端、设备和输出分开，适合平板旁的工具。当前更影响操作的是连接和空状态引导，以及任务密集时的辨认。

Android 顶部工具栏横排多个按钮，连接状态固定为 260dp，外层留白与侧栏也比较大。虽然内容区会在 750dp 以下改为纵向排列，顶部并未同时适配。代码显示手机窄屏有裁切风险，需要在设备或模拟器上验证，不能用横屏平板截图证明手机可用。

默认 A/B 字母需要用户阅读说明才能理解；“逐个提醒”和“全部完成”的文字应持续可见。红点兼顾完成与待处理时，也需要配合状态文字，不能只靠颜色。长窗口标题、多个相似任务和大段终端输出会挤占注意力，后续可加入搜索、置顶与状态筛选。

空列表与未选终端提示需要改为可执行的连接和选择步骤。新手向导、手机布局与语言切换列入[路线图](ROADMAP.md)，留待后续功能迭代。

## 本次补齐什么

此次发布建立实际代码入口与 v1.2.0 下载，Windows 包通过文件白名单组装，自动排除本机状态，提供 SHA-256。CI 检查构建、状态行为与文档，标签触发生成可下载测试产物。开发签名与升级限制会在下载说明中明确写出。

仓库首屏增加构建、发布和许可状态，补充适用场景与路线图入口。项目站提供中英文静态页面、各自 canonical、语言替代链接、社交分享元数据、结构化软件资料和站点地图。About 和 Topics 按真实功能配置；版本标签用于 Release，两者分别承担搜索分类与版本管理。

## 接下来怎样验证改进有效

先找 5 至 10 位符合条件、没有参与开发的人，从下载开始独立完成连接。记录他们卡在哪一步、是否需要帮助，以及能否在平板上完成一次输入和收到提醒。首次价值的目标可以设为 5 分钟内，但要用实际记录验证。

接着观察 GitHub 14 天流量、Release 下载变化和用户自愿反馈。将“看过项目”“下载”“连接成功”“一周后仍使用”分别记录，定位具体障碍。客户端保持本地优先，初期可以用自愿回访收集结果，无需先加入跟踪 SDK。

传播材料应是一段真实的 30 至 60 秒录屏，从电脑任务开始，到平板输入或授权，再到完成横幅。发布时围绕这一场景讲清兼容条件。持续回答可复现问题、合入贡献和提供可靠版本，才有机会把首次关注变成长久使用。
